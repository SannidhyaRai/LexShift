# M1 postings compression: sizes and decode times on the real index

Generated by `python -m m1_index.compress` on 2026-11-21 over the index of 4,819 judgments: 183,673 terms, 3,826,321 postings (document numbers) and 17,259,114 positions. Every encoded list was decoded back and compared with the index's arrays (12 s); all of them match.

## Sizes

| Encoding | Document numbers | Positions | Total | vs raw |
|---|---:|---:|---:|---:|
| Raw arrays (4-byte integers, the live in-memory format) | 14.6 MB | 65.8 MB | 80.4 MB | 100% |
| gzip of the raw arrays (level 6) | 6.0 MB | 33.7 MB | 39.7 MB | 49% |
| Gaps + variable-byte | 4.0 MB | 24.9 MB | 28.9 MB | 36% |
| Gaps + Elias gamma | 2.6 MB | 28.3 MB | 30.9 MB | 38% |
| Gaps + variable-byte, then gzip | 2.4 MB | 21.0 MB | 23.5 MB | 29% |

Bits per entry: document gaps 8.76 (VB) and 5.69 (gamma); position gaps 12.09 (VB) and 13.77 (gamma). Largest gap: 4,819 between documents, 85,832 between positions.

Not in the table: the per-zone term counts (`p_zc`, 8 bytes a posting) and the posting offsets (`p_off`, derivable from the counts), which the decoder needs to know where each zone's run of positions restarts, and the vocabulary itself. The whole index file on disk (`index.pkl.gz`, all arrays and tables, gzip) is 52.7 MB.

## Decode time (every posting list of the index to Python integers)

| Encoding | Decode all postings | Encode all postings |
|---|---:|---:|
| Raw arrays (slice to a list) | 0.17 s | none |
| gzip (decompress, then to a list) | 0.36 s | 5.9 s |
| Variable-byte | 0.90 s | 8.9 s (VB and gamma together, including building the gap streams) |
| Elias gamma | 3.71 s | (with VB) |

## Decision

The live index keeps the raw arrays in memory. VB would cut the postings to 36% of their size and make reading a query's postings at most 4.9 ms slower (worst case `punishment for murder under section 103 BNS`: 6.1 ms instead of 1.2 ms), so search would still stay well under one second and the budget would allow the change. It is not made because nothing needs it: the memory saved (51.6 MB) does not matter on a laptop, the file on disk is already gzip-compressed, and other code reads the arrays directly (the Index page in `app/m1_view.py` uses `index.p_doc`), so a new live format would mean changing code outside M1 for no gain the demo can show. The encoders stay here, tested, for the report and the video. See DECISIONS.md D-040.
